# PAIRES ET FAMILLES DE CAPTURES PERSONA LEGITIMEMENT IDENTIQUES (tache 665,
# familles ajoutees a la tache 685).
#
# Le controle de fin de run (`tool/persona_shot_check.py`) refuse un run ou deux
# marqueurs DIFFERENTS rendent une image au contenu identique : c'est la
# signature du retard de capture (l'image d'un ecran servie pour un autre), le
# defaut trouve au 645-05b (memoire #101082).
#
# Mais deux captures d'un MEME ecran peuvent etre identiques pour de bonnes
# raisons : une action sans effet visible, un ecran deja dans l'etat attendu.
# Ces cas-la se declarent ICI, AVEC LEUR RAISON. Rien n'est tolere par defaut,
# et depuis la tache 685 une declaration SANS RAISON ECRITE fait rougir le run :
# la lever oblige a regarder l'image, ce qui est exactement le but.
#
# DEUX FORMES :
#   <marqueur_a> <marqueur_b>                  # pourquoi ces deux-la
#   groupe: <marqueur_a> <marqueur_b> <...>    # pourquoi toute la famille
# La famille tolere toutes ses paires INTERNES, et rien d'autre.
#
# POURQUOI LA FAMILLE EXISTE, ET CE QU'ELLE REPARE (mesure du 05/10,
# memoire #101219). La regle de doublon compare l'image ENTIERE, barre d'etat
# comprise : UN pixel d'horloge suffit a declarer « differentes » deux captures
# d'un ecran ou rien ne s'est passe. LE GROUPEMENT CHANGE DONC D'UN RUN A
# L'AUTRE. Sur la carte immobile de S1, le run de 06:42 a rendu le groupe
# {tick_05, tick_06, tick_07, apres_gps, apres_sos} et celui de 08:03 les
# groupes {tick_03..tick_06} puis {apres_gps, apres_sos} : les MEMES images, un
# decoupage different. Declarer paire par paire obligeait a ecrire les 78 paires
# d'une famille de treize pour que le verdict soit stable — ou a laisser le run
# rouge un jour sur deux, ce qui rend le controle inutilisable et donc
# contourne. Le controle, lui, n'est pas affaibli : il compare toujours les
# images entieres, et tout doublon hors famille declaree reste ROUGE.
#
